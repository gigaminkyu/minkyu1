# CLAUDE.md — Schema for a Self-Maintaining Knowledge Base

This repository is an **LLM-maintained knowledge base**. It follows the pattern
in *LLM-WIKI.md: Field Notes on a Knowledge Base That Maintains Itself*
(ingested at `raw/2026-07-03-llm-wiki-field-notes.md`).

This file is the **schema**. It holds the rules and belongs to both the human
and the model. When you (the model) operate on this repo, this file is your
operating manual. Read it fully before touching anything.

> The human owns judgment and the raw record. The model owns the bookkeeping.
> The wiki is a compiled artifact that compounds rather than a pile that grows.

---

## The three layers (never blur them)

| Layer        | Path        | Owner        | Mutable?                          |
| ------------ | ----------- | ------------ | --------------------------------- |
| Sources      | `raw/`      | Human        | **No** — append only, never edit  |
| Wiki         | `wiki/`     | Model        | Yes — regenerated by the model    |
| Schema       | `CLAUDE.md` | Both         | Yes — by agreement                |

If you find yourself editing a file in `raw/`, or the human is hand-tuning a
page in `wiki/` to win an argument, stop. The boundaries are what make this
system trustworthy.

---

## The rules

### 1. Sources are immutable
Everything saved lands in `raw/` and is **never edited after it lands**.
Articles, transcripts, PDFs, screenshots, notes — this is the source of truth.
If a source is wrong, add a *correcting source*; do not rewrite history. Editing
a raw file by hand creates two systems of record and no way to tell which is
true.

### 2. Separate the layers
`raw/` holds immutable sources (human's). `wiki/` holds generated pages
(model's). `CLAUDE.md` holds the rules (shared). Do not mix responsibilities
across them.

### 3. The model owns the wiki
The human rarely writes a wiki page by hand. Their job is to choose what enters
`raw/`, to ask questions, and to think. The model's job is the part humans
avoid: summarizing, cross-referencing, filing under the right entity, and
updating neighbors when something new arrives. If the human is doing the
bookkeeping, the schema is underspecified — fix the schema, not the symptom.

### 4. Compile, don't retrieve
This is **not RAG**. RAG re-derives an answer from raw chunks on every query and
accumulates nothing. Here, sources are compiled **once** into structured, linked
pages, and questions are answered from that built artifact. `raw/` is source
code, the model is the compiler, `wiki/` is the executable, queries are runtime.
Compiled knowledge compounds; retrieved knowledge is rediscovered every time.

### 5. Ingest one source at a time
Drop a single file into `raw/` and ingest it. A good ingest is **not** one new
page — it is tracing the implications of that source across the whole graph,
touching every page the new fact changes. Batch-importing everything at once
produces a dump, not a wiki, because nothing gets linked while the pile is still
forming. See the **Ingest workflow** below.

### 6. Link everything
Every page connects to others through wikilinks (`[[Page Name]]`), and every
link is a visible edge in the graph. A page that appears in five other pages but
links to none is a sign the ingest was lazy. The value of the system is in the
edges, not the nodes.

### 7. Navigate by index
Answer a question by reading `wiki/index.md`, following the few relevant pages,
and synthesizing — **not** by loading the whole vault into context. Keep the
index honest: if it has stopped reflecting the territory, it needs a pass. A
well-indexed wiki of hundreds of pages stays fast; brute-forcing the corpus on
every question does not scale.

### 8. Lint the knowledge
Treat the wiki like code and run health checks (see **Linting** below). Find
contradictions between pages, surface low-confidence claims, flag orphan pages,
and catch entities that drifted into two spellings. A contradiction is
*information*, not an error to paper over — it usually means two sources disagree
and you now know where to look. Skipping the lint is how a wiki quietly rots.

### 9. Start small
Begin with ~10 sources, not 10,000. Get ingest, query, and lint to feel natural
before adding a search engine, elaborate frontmatter, or a 20-rule schema. Early
pages will be messy and naming conventions will change — that is normal. A small
wiki you actually feed beats a beautiful architecture you abandon in week three.

## Directory layout

```
.
├── CLAUDE.md          # this schema (shared)
├── README.md          # human-facing overview
├── raw/               # immutable sources (human owns)
│   └── <YYYY-MM-DD-slug>.<ext>
└── wiki/              # compiled pages (model owns)
    ├── index.md       # the navigation hub — start every query here
    └── <entity>.md    # one page per entity/topic
```

---

## Source naming (`raw/`)

- Filename: `YYYY-MM-DD-slug.ext` where the date is when the source was captured.
- Never rename or edit a source after it lands. Corrections are *new* sources.
- Prefer text-extractable formats. For a PDF/image, drop the original **and** a
  `.md` transcript alongside it so the content is greppable and linkable.

## Wiki page format (`wiki/`)

Every page starts with minimal frontmatter, then prose, then explicit links and
provenance:

```markdown
---
title: Entity Name
type: concept | person | tool | project | event | claim
updated: YYYY-MM-DD
sources: [raw/2026-07-03-llm-wiki-field-notes.md]
confidence: high | medium | low
---

# Entity Name

Compiled summary in prose. State claims plainly; where sources disagree, say so.

## Links
- [[Related Page A]] — why they connect
- [[Related Page B]] — why they connect

## Sources
- `raw/2026-07-03-llm-wiki-field-notes.md` — what this source contributed
```

Keep frontmatter minimal per Rule 9. Add fields only when a real query needs
them.

## Ingest workflow (Rule 5)

When a new file appears in `raw/`:

1. **Read** the source fully.
2. **Extract** the entities, claims, and relationships it introduces.
3. **File** each into the right existing page, or create a new page. One entity =
   one page. Reuse pages; do not fork near-duplicates (Rule 8, drift).
4. **Link** every new page to its neighbors, and add back-links from neighbors
   to it (Rule 6). Ingest is done when the graph reflects the new fact, not when
   one page is written.
5. **Update `wiki/index.md`** so the new/changed pages are reachable (Rule 7).
6. **Record provenance**: list the source under `sources:` on every page it
   touched.
7. **Lint** the pages you touched before finishing (Rule 8).

## Linting (Rule 8)

Run these checks and report findings; do not silently "fix" a contradiction —
surface it.

- **Contradictions**: claims across pages that disagree → flag with both sources.
- **Orphans**: pages with no inbound or no outbound links → link or justify.
- **Drift**: one entity under two names/spellings → merge to one page, redirect.
- **Stale index**: pages missing from `index.md`, or index entries pointing at
  deleted pages.
- **Low-confidence claims**: anything marked `confidence: low` or unsourced →
  list for the human's attention.

---

## Quick reference for the model

- To **answer a question**: start at `wiki/index.md`, follow links, synthesize.
  Do not read the whole vault.
- To **ingest a source**: follow the Ingest workflow above, end to end.
- To **audit health**: run the Linting checks and report.
- Never edit `raw/`. Never hand-write `wiki/` on the human's behalf beyond what
  the source supports. When in doubt, fix the schema, not the instance.
